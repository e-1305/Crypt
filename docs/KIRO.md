# How CRYPT was built with Kiro

CRYPT was built with Kiro specs, steering, hooks and custom agents (see "Custom agents": three agents, two with config files), plus its own MCP server. Strategy, review gates and some CI and conflict fixes came from a human-supervised AI CTO (Claude); the commits are listed under "Process note". Specs were used for real in Kiro Web sessions. Steering was read on instruction, not observed as auto-loaded. Hooks are configured and CI-checked but were not observed firing in Kiro Web (see "Limits"). Every count below comes from `npm run kiro:stats`, not from typing.

## Limits

- **Hooks were not observed firing in Kiro Web.** The state is: 7 hook files are configured (`PostFileSave` and `PostToolUse` twins, `Stop`, `SessionStart`), CI checks them, and 5 lines in `docs/evidence/hook-runs.jsonl` come from running the wrappers by hand (trigger `manual`). Zero runs were recorded in a Kiro session. The probable cause is the workspace layout found in PR #94: in Kiro Web the session workspace root is `/projects/sandbox` and the repository is cloned into a subfolder, so the repository's `.kiro/` is probably not loaded as session configuration. That is an inference, not something Kiro reported. A desktop IDE or CLI session with the repository as workspace root is where these hooks apply. As of this change still zero real runs are recorded, and the likely cause of the Kiro Web gap is unchanged. If real IDE or CLI runs are added, the line "Hook runs recorded in a real Kiro session" in the numbers block will show them.
- **Kiro CLI in GitHub Actions (ready, not yet run).** Kiro documents that CLI V3 loads workspace hooks from `.kiro/hooks/*.json` ([hook types](https://kiro.dev/docs/hooks/types/)) and that headless runs use `kiro-cli chat --v3 --no-interactive` with an API key in the environment variable `KIRO_API_KEY` ([headless mode](https://kiro.dev/docs/cli/headless/)). `.github/workflows/kiro-hooks.yml` runs that session with the repository as workspace root. Not verified: that every trigger fires in a headless session. That stays unproven until a run exists, and a hook that does not fire leaves no line. The workflow needs one repository secret before it can run. Steps:
  1. Create an API key in Kiro. API keys are available on Kiro Pro, Pro+, Pro Max and Power plans; an administrator enables key generation for managed accounts ([headless mode](https://kiro.dev/docs/cli/headless/), [authentication](https://kiro.dev/docs/getting-started/authentication/)).
  2. In the GitHub repository open Settings > Secrets and variables > Actions > New repository secret. Name it `KIRO_API_KEY` and paste the key as the value.
  3. In Settings > Actions > General, under Workflow permissions, allow GitHub Actions to create pull requests.
  4. Open Actions > kiro-hooks > Run workflow.
  5. Review the pull request the run opens. It changes only `docs/evidence/hook-runs.jsonl`, and the session output is in the run's artifact. A run where no hook fired fails the job and opens no pull request. A pull request opened with `GITHUB_TOKEN` does not start CI, so the workflow runs `hook-evidence-check.mjs` itself before it pushes. Known risks: the Kiro CLI installer is an unpinned remote script (Kiro publishes no checksum), and the agent has write tools in the checkout. The checkout keeps no token, and the token reaches only the final push step.
- Details of the attempts. The File Save trigger (`PostFileSave`) is not supported in Kiro Web ([Kiro hook types](https://kiro.dev/docs/hooks/types/)). Issue #87 added `PostToolUse` (matcher `write`), `Stop` and `SessionStart` hooks that Kiro Web does support. The session that wrote them did not load them (hooks are read at session start), and editing matching files there wrote no line. Issue #91 repeated the attempt in a fresh session with the hooks already on `main`: one edit per hook filter (`src/**/*.ts`, `src/necromancer/**`, `.kiro/specs/hook-evidence/tasks.md`, `package.json`, `web/copy.js`) wrote no new line and showed no hook error, and no `SessionStart` or `Stop` line appeared either. Every line in `docs/evidence/hook-runs.jsonl` carries the trigger `manual`.
- **Steering was not observed as auto-loaded in Kiro Web.** For the same layout reason it is not claimed. What is verifiable: every Kiro issue explicitly told the agent to read `.kiro/steering/` first, and the rules show up in the code and tests (three examples under "Steering").
- The safety claims rest on tests (property-based, run in CI) and on the scripts named here, not on a recorded Kiro session.
- Nothing here measures how much time Kiro saved. There is no such measurement.
- All rows change only when the `stats` workflow on `main` runs `npm run kiro:stats -- --write`. Between runs the numbers can lag the repository. A test checks the shape of the block, not the values.

Triggers by surface, from the [Kiro hook types page](https://kiro.dev/docs/hooks/types/):

| Trigger | IDE | CLI V3 | Kiro Web | Used here |
|---|---|---|---|---|
| File Save (`PostFileSave`) | yes | yes | no | the five save hooks, for IDE and CLI users |
| Post Tool Use (`PostToolUse`, matcher `write`) | yes | yes | yes | one twin per save hook, same filter regex |
| Agent Stop (`Stop`) | yes | yes | yes | `failsafe-guard-on-stop.json` (guard over all of `src/` and `bin/`) |
| Session Start (`SessionStart`) | yes | yes | yes | `session-start-log.json` |

The `PostToolUse` twins run `run-logged.sh` with `CRYPT_HOOK_FILTER` set to the save hook's regex. The wrapper reads the written path from the session JSON on STDIN, does nothing when the path does not match, and otherwise runs the check and logs `trigger: "PostToolUse"`. The tool IDs of the write tools were not observed (no run has fired), so `write` is the documented category and nothing more is claimed.

The hooks and their scripts were added in `65c945c`; the A2 spec is `771e8be`.

### Hook runs
Each hook file has a `command` action that runs `scripts/hooks/run-logged.sh`. The wrapper runs the check, keeps its exit code, and appends one line `{ts, hook, trigger, file, exit, summary}` to `docs/evidence/hook-runs.jsonl`. It never stores the event JSON, a secret or an author name. `hook-evidence-check.mjs` in CI checks every hook file (each save hook needs its `PostToolUse` twin) and every line. A line may carry one optional key, `source`. The only value is `kiro-cli-ci`, set by `scripts/ci/kiro-hooks-collect.mjs` in the `kiro-hooks.yml` workflow on lines that the wrapper wrote during a headless Kiro CLI session. A line with a source must have a trigger other than `manual`. The spec is `.kiro/specs/hook-evidence/`. The trace and attribution hooks keep their agent prompt as a second entry with the same matcher.

The numbers block has three counts. "Hook runs by hand (manual)" counts lines whose trigger is `manual`. "Hook runs recorded in a real Kiro session" counts lines whose trigger is not `manual`; a line counts as real only if its trigger is not `manual`. "of which Kiro CLI in GitHub Actions" counts the real lines with `"source":"kiro-cli-ci"`. Not every hook has to appear: the table below reports each hook on its own.

## MCP
**Consumed.** Kiro reads `.kiro/settings/mcp.json`, which names one server: CRYPT's own. No third-party MCP server is configured or used.

**Produced.** `npm run mcp` runs [`scripts/mcp.ts`](../scripts/mcp.ts), the CRYPT MCP server on stdio ([`src/mcp/`](../src/mcp/core.ts), tests in [`tests/mcp.test.ts`](../tests/mcp.test.ts)). Read tools: `list_limbs`, `get_limb`, `census_summary`, `audit_tail`. Write tools: `request_graft` (through the watcher, never calls GitHub) and `seal`. Read tools are auto-approved in the config; write tools are not.

## Property-based tests
The count of call sites is in the numbers block. The full invariant list is in the appendix. The three that carry the most weight:

1. After SEAL no request is ever written (failsafe rule 7): `tests/watch.test.ts`, test "property (rule 7): after SEAL no request is ever written".
2. KEV always outranks non-KEV, so the ranking cannot be argued down by a score (sla-policy): `tests/exhume.test.ts`, test "KEV always outranks non-KEV".
3. No output field contains a git author or committer, read through a real git repo (blameless): `tests/exhume.test.ts`, test "no output field contains a git author or committer, with a real git repo read through the CLI filesystem".

## CI guard jobs
`.github/workflows/ci.yml` runs these jobs on every pull request:

- `test`: typecheck, spike, raise and necromancer checks, then vitest with `CRYPT_NUM_RUNS=1000`.
- `failsafe-guard`: `scripts/ci/failsafe-guard.sh`, the same rules as the save hook.
- `visual-qa`: screenshots at several sizes and a Lighthouse accessibility check.
- `pack-install`: tarball installed into an empty project on the Node versions listed in `.github/workflows/ci.yml`.
- `kiro-docs`: `npm run kiro:stats` and `npm run kiro:stats -- --check-links`, on a full-depth checkout so commit SHAs resolve. It does not check the generated stats blocks.

Generated numbers (the block above, the stats blocks in `docs/DEVPOST.md` and `docs/BLOG.md`, and `docs/img/kiro-timeline.svg`) are regenerated only on `main` by `.github/workflows/stats.yml`, which commits `chore(stats): regenerate [skip ci]`. Do not run `kiro:stats --write` or `kiro:timeline` in a PR.

### Design notes

- **`(at)` in owner names.** The plate prints `@team`. The story text prints `(at)team`, because `@` is an escape character in Inform 6 strings and `src/raise/sanitize.ts` replaces it (with brackets, quotes and control characters) for every generated string. We kept the sanitiser whole and explain the spelling in the manual's "How it works".
